## Decision gate 2 — Local development tools

Run on your **Mac** in Terminal. Commands are intentionally read-only. A missing tool should print `not installed` rather than stopping the script.

```bash
set -u
echo "== Operating system and architecture =="
sw_vers
uname -m

echo "== CPU and RAM =="
sysctl -n hw.ncpu
sysctl -n hw.memsize

echo "== Installed tools =="
for tool in git docker kubectl kind helm aws terraform; do
  if command -v "$tool" >/dev/null 2>&1; then
    printf '%s: %s\n' "$tool" "$(command -v "$tool")"
  else
    printf '%s: not installed\n' "$tool"
  fi
done

echo "== Version commands (where available) =="
command -v docker >/dev/null 2>&1 && docker --version || true
command -v kubectl >/dev/null 2>&1 && kubectl version --client || true
command -v kind >/dev/null 2>&1 && kind version || true
command -v helm >/dev/null 2>&1 && helm version --short || true
command -v aws >/dev/null 2>&1 && aws --version || true

echo "== Docker engine availability =="
command -v docker >/dev/null 2>&1 && docker info --format 'Server: {{.ServerVersion}} | CPUs: {{.NCPU}} | Memory bytes: {{.MemTotal}}' || true
```

`docker info` reads the configured engine and may fail if Docker Desktop is not running. No images are pulled and no cluster is created.

## Decision gate 3 — Existing Kubernetes contexts

On the Mac:

```bash
kubectl config get-contexts
kubectl config current-context
```

**Stop before any `kubectl apply` or delete command.** Verify that the selected context points to the intended isolated lab cluster. Never assume the default context is a safe target.

If Kubernetes tooling is not installed, note that fact; do not run the commands.

## Decision gate 4 — Runtime choice

| Runtime | Suitable for | Constraints |
| --- | --- | --- |
| `kind` | Low-cost, isolated foundational Kubernetes validation, supported by upstream Online Boutique guidance | Requires sufficient local Docker CPU/RAM/disk; no native cloud LoadBalancer |
| Amazon EKS | AWS-managed Kubernetes lab if TWN assignment calls for it or chosen as a justified extension | Cluster, nodes, load balancers and public network resources incur ongoing costs; use explicit cleanup/budget limits |
| Other managed Kubernetes | Use only when the actual TWN assignment specifies it | Evaluate provider-specific permissions, networking and cleanup |

**Initial preference:** Evaluate `kind` for fast local verification, then use EKS only if required or deliberately selected for Capstone 04. This is not a commitment to build a larger platform.

## Manifest validation strategy (after runtime choice)

1. Record the exact source Git commit SHA, manifest version, required namespaces and image references.
2. Check referenced container images can be pulled on the chosen runtime.
3. Review potential `Service` type `LoadBalancer`: on `kind`, access should use `kubectl port-forward` unless another ingress/load-balancer mechanism is specifically justified.
4. Review existing probes, resource requests/limits, security contexts and Redis `emptyDir` limitations.
5. Use a dedicated Kubernetes namespace, and verify current context and namespace before applying.
6. Prefer upstream `release/kubernetes-manifests.yaml` with a minimal, separately versioned customization where necessary; do not hand-edit generated release YAML.
7. Define the exact cleanup operation before provisioning.
