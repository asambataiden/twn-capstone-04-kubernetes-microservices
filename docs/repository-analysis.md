## Application behavior

Online Boutique is an e-commerce demonstration: users browse products, add items to a cart and complete a simulated checkout. There are eleven functional services plus Redis for cart storage. The frontend communicates with backend APIs, including gRPC-based services.

| Component | Existing role |
|---|---|
| `frontend` | HTTP entry point and browser UI |
| `productcatalogservice` | Product listing and search |
| `currencyservice` | Currency conversion |
| `cartservice` | Cart operations backed by Redis |
| `redis-cart` | Cart data store (supporting infrastructure) |
| `checkoutservice` | Orchestrates order processing |
| `paymentservice` | Mock payment authorization |
| `shippingservice` | Mock shipping calculation/shipment |
| `emailservice` | Mock order confirmation |
| `recommendationservice` | Product recommendations |
| `adservice` | Contextual ads |
| `loadgenerator` | Synthetic traffic generation; not customer-facing |

## Verified Kubernetes facts

1. `kubernetes-manifests/README.md` warns that its manifests **cannot be deployed directly** without Skaffold substituting image references; it directs users to `release/` for prebuilt public images.
2. `release/kubernetes-manifests.yaml` is marked **autogenerated — do not manually edit**, and embeds versioned public images for the services.
3. `frontend.yaml` already defines readiness/liveness HTTP probes, CPU/memory requests and limits, non-root security settings, a `ClusterIP` Service and an optional `LoadBalancer`-type external Service.
4. `cartservice.yaml` uses a gRPC health probe, and points at `redis-cart:6379`.
5. `redis.yaml` uses an `emptyDir` for Redis data: Pod replacement can discard cart state; do not claim durability.
6. `helm-chart/values.yaml` already supports opt-in network policies, platform options and configurable services. Avoid rebuilding what is already supplied.
7. `docs/product-requirements.md` emphasizes maintaining the normal user journey and preserving `kind` compatibility and a simple default demo.

## Unknowns and unverified items

- Exact TWN Capstone 04 submission/assessment requirements have **not** been provided or verified.
- Kubernetes provider, runtime version, available resources and network exposure method are **not** selected.
- Image pull availability, startup time, end-to-end checkout, probes and recovery have **not** been tested in a live cluster.
- Existing manifests may need environment-specific adjustment; identify changes using a dedicated overlay rather than editing autogenerated release output.

## Initial recommendation

Use upstream release manifests as a reproducible starting baseline in a local `kind` cluster if host resources allow. First run manifest/API validation, then deploy, inspect Pod health, reach frontend with port-forward, test browsing/cart/checkout and capture evidence. Only then introduce one or two controlled operational improvements.
