### 3. Validate the versioned manifest without creating workloads

```bash

bash scripts/capstone04-deploy.sh plan
```

The script retrieves a pinned file from the public source repository, verifies expected markers, and performs a **server-side dry run** against the explicitly named lab context and namespace.

### 4. Deploy only after preflight and scope review

```bash
bash scripts/capstone04-deploy.sh deploy
```

The script repeats server-side validation and then requests an explicit interactive confirmation before applying resources. Unlike the status/plan commands, this is a real workload change.

### 5. Validate Deployment readiness and frontend

```bash
kubectl --context k3d-twn-capstone04 -n online-boutique get deploy,pods,svc
kubectl --context k3d-twn-capstone04 -n online-boutique rollout status deployment/frontend --timeout=180s
kubectl --context k3d-twn-capstone04 -n online-boutique port-forward service/frontend 8080:80
```

The port-forward command occupies its own terminal. In a **second Terminal** visit `http://localhost:8080`. Confirm product browsing, add to cart and simulated checkout. If other Deployments fail to become ready, inspect events and logs before concluding the application is healthy.

## Safety and recovery

- All writes use explicit `--context k3d-twn-capstone04` and `--namespace online-boutique`.
- Existing AWS EKS contexts and banking clusters are never deployment targets.
- This script does **not** provision a cloud cluster, prune Docker data or delete resources.
- Initial online-shop traffic uses local port-forward. A manifest may include `LoadBalancer` Service semantics, but we do not require public exposure.
- Do not claim Redis persistence. The upstream demo's Redis uses ephemeral `emptyDir`.
- Cleanup/undeploy is intentionally not automated yet; define a safe, namespace-scoped process once deployment behavior is verified.
- Image compatibility on Apple Silicon and actual memory adequacy must be validated on the user's environment, not inferred from static manifests.

## Live deployment follow-up — runtime troubleshooting

Subsequent operator output confirms **11/12 Deployments Ready and Available**, including `frontend` (successful rollout), and **loadgenerator 0/1** with `Init:CrashLoopBackOff` for init container `frontend-check`. The `cartservice` Pod is currently Ready but had **5 restarts**; liveness probe / connection-reset events need investigation.

A second `deploy` run returned `unchanged` for all resources, confirming declarative reapplication without modifications.

Local `8080` port-forward failed with `address already in use`; a `curl -I http://localhost:8080` returned a **302 redirect to /login**, which cannot be credited as an Online Boutique response because the port-forward never started. Prefer a different local port (e.g. `18080`) rather than terminating unrelated processes.

## Incident follow-up: frontend HTTP 500 / cartservice crash

Operator findings:
- `cartservice` observed in `CrashLoopBackOff` (five restarts) while `redis-cart` was Running without restarts.
- Previous cartservice logs show `.NET` service startup and health messages, then `System.NullReferenceException` executing `GetCart` and fatal `System.AccessViolationException`. The service is not healthy merely because it temporarily reports Ready.
- Redis output shows version 8.10.2 startup, module initialization and `Ready to accept connections tcp`; it also warns that Redis has no authentication and is not protected by network restrictions (acceptable only as a confined local demo, not production hardening).
- Redis and cartservice EndpointSlice objects exist; the presence of an endpoint alone is not proof that its backing application answers requests.
- Local frontend returned HTTP 500; loadgenerator `frontend-check` retrieved that same status and exited with code 1.
- **Proposed investigation:** verify actual node/pulled image architecture and container termination reason. A compatibility issue under Apple Silicon/amd64 emulation is plausible, not proven. Application fault and runtime/library mismatch remain possibilities.

### Read-only diagnostic gate

```bash
kubectl --context k3d-twn-capstone04 get node -o custom-columns=NAME:.metadata.name,ARCH:.status.nodeInfo.architecture,OS:.status.nodeInfo.operatingSystem
docker buildx imagetools inspect gcr.io/google-samples/microservices-demo/cartservice:v0.8.0
kubectl --context k3d-twn-capstone04 -n online-boutique describe pod -l app=cartservice
kubectl --context k3d-twn-capstone04 -n online-boutique get pods -l app=cartservice -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .status.containerStatuses[*]}{.name}{": "}{.lastState.terminated.reason}{" exit="}{.lastState.terminated.exitCode}{"\n"}{end}{end}'
```

Do not retag images, force amd64 node emulation, switch Redis versions or disable health probes until these checks explain the behavior. Any fix must be committed as a reproducible, scoped configuration change and retested against frontend/cart/loadgenerator.

## Confirmed container architecture mismatch — 24 October 2026

Operator verified the Kubernetes node reports `linux/arm64` and the source-pinned `gcr.io/google-samples/microservices-demo/cartservice:v0.8.0` image reports `linux/amd64` using:

```bash
docker buildx imagetools inspect --format '{{json .Image}}' \
  gcr.io/google-samples/microservices-demo/cartservice:v0.8.0 \
  | jq -r '"\\(.os)/\\(.architecture)"'
```

This confirms the image/node mismatch. It is a strong explanation for `.NET` instability under architecture emulation, **but does not uniquely prove the origin of the managed and native runtime faults**. The cart container had prior termination code 133 and multiple restarts.

**Controlled resolution plan:** inspect a candidate upstream ARM64 cart-service image such as v0.10.3 (upstream release notes report ARM64 support), pin its immutable digest only after validation, assess cross-version protobuf/gRPC compatibility with remaining v0.8.0 services, then apply a separately versioned, narrowly scoped overlay. No runtime image change has been made yet. If no compatible image exists, consider a reproducible native ARM64 build using the existing source/contract instead of replacing the whole stack.
